# Contributing

This repository is a Rust workspace with a `dev` → `main` branching model and a
changelog that is derived from the commit messages. That means your commit
subjects are release notes: they get read by people, not just by `git log`. The
rules below are what the CI enforces, so following them is also the fastest way
to a green PR.

## Branch model

`dev` is the default branch and the only place work lands. `main` is the release
branch: it moves only by merging `dev` into it, and every such merge that
carries a new version number publishes a GitHub Release.

```
feature/rawinput-got-guard ─┐
fix/pakfile-case            ─┼──▶ dev ───(PR, version bump)───▶ main ──▶ release v2.0.1
docs/readme-release-model   ─┘      ▲                            │
                                    └── nightly prerelease       └── tag v2.0.1
                                        (weekly, built from dev)     CHANGELOG.md commit
```

- Branch off `dev`, PR back into `dev`.
- **Nobody commits directly to `main`.** A push to `main` is a release event, so
  a stray commit there is either a no-op or a release you did not mean to cut.
- The version lives in exactly one place: `[workspace.package] version` in the
  root `Cargo.toml`. The three crates inherit it with `version.workspace = true`.
  Nothing else records the version — no per-crate version, no constant in the
  source, no hand-maintained line in the README.

## Commit convention

[Conventional Commits](https://www.conventionalcommits.org), required:

```
type(scope)!: subject
```

Subject in the imperative mood ("validate", not "validated"/"validates"), no
trailing period. The scope is optional but strongly encouraged, because it is
what makes a generated changelog readable.

| type | changelog section |
|---|---|
| `feat` | Added |
| `fix` | Fixed |
| `perf` | Performance |
| `refactor` | Changed |
| `docs` | Documentation |
| `revert` | Reverted |
| `test` | — kept out of the changelog |
| `ci` | — kept out of the changelog |
| `build` | — kept out of the changelog |
| `chore` | — kept out of the changelog |

`test`, `ci`, `build` and `chore` are valid commits; they simply do not appear
in the release notes. Housekeeping should not push a real change off the page.

**Breaking changes** are marked with a `!` before the colon
(`feat(hook)!: …`) or with a `BREAKING CHANGE:` footer in the commit body. They
are collected into their own section of the changelog and mean a major version
bump.

Suggested scopes, matching the tree:

`core`, `hook`, `patcher`, `linux`, `windows`, `sig`, `elf`, `pakfix`,
`rawinput`, `viewpunch`, `fastdl`, `engine`, `sourcejump`, `ci`, `docs`.

Real examples:

```
fix(hook): validate the SDL_PollEvent GOT slot before writing
feat(sourcejump): show the world record on map load
refactor(sig): return match offsets instead of raw pointers
docs(readme): describe the dev/main release model
feat(hook)!: rename BHOPFIX_NO_FORCE to BHOPFIX_KEEP_RAWINPUT
chore(release): 2.0.1
```

CI enforces this. The `commits` job in `ci.yml` validates every commit subject
pushed to `dev` and every commit in a pull request, and when one does not parse
it fails with the list of allowed types. Fix it with `git commit --amend` or an
interactive rebase and force-push the branch; there is no bot that rewrites your
history for you.

## How the changelog is produced

`CHANGELOG.md` is generated by [git-cliff](https://git-cliff.org) from the commit
history, configured by `cliff.toml` at the repo root. Every commit since the
previous tag becomes one bullet, grouped by type, with a short SHA link.

It is written **at release time**, not on every push, so `dev` never collects
bot commits and you never rebase across a generated file. To see what the next
release's notes look like right now, let CI tell you: every push to `dev` and
every PR renders the pending changelog into the GitHub Actions **job summary**
of the `changelog-preview` job. If a bullet reads badly there, the commit subject
is the thing to fix.

**A hand-written section wins.** If `CHANGELOG.md` already contains a
`## [<version>]` section for the version being released, the release uses that
prose verbatim and generates nothing. That is how the curated `2.0.0` entry
survives regeneration. Leave the section out and the commits write it for you —
which is the normal case, and the reason there is nothing to edit by hand in a
regular PR.

## Checks to run before pushing

The same three things CI's `lint` and `test` jobs run:

```sh
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

`clippy` runs with `-D warnings` in CI, so a warning is a failure there even
though it is not locally.

**CI's clippy is whatever `stable` is today, which may be newer than yours.**
A newer stable ships new lints, and `clippy::all` is denied workspace-wide, so
code that is clean on your machine can fail CI on a lint that did not exist
when you wrote it. This is not hypothetical: 2.0.0's first CI run failed on
`chunks_exact_to_as_chunks`, added in clippy 1.98, against code that passed on
1.97. Before pushing something lint-sensitive:

```sh
rustup update stable
cargo +nightly clippy --workspace --all-targets -- -D warnings
```

Nightly clippy sees the lints stable is about to get, so it catches this class
of failure locally. The weekly canary (`schedule.yml`) exists for the same
reason: it runs stable, beta and nightly every Monday so toolchain drift is
reported on a quiet week instead of in the middle of a release.

The resolver tests exercise the *installed* game when it is present and
self-skip when it is not. On a bare runner they pass without proving anything;
on a machine with CS:S installed they are the real check — a genuine "did a game
update move the lookups?" test. If you have the game, run `cargo test
--workspace` there and say so in the PR.

### Windows changes

CI compiles, links, tests, and cross-links the Windows controller/DLL pair, but
GitHub runners cannot launch CS:S. A PR touching
`crates/bunnyhopfix/src/windows*` or
`crates/bhopfix-hook/src/windows*` must state whether it ran against a real
native x64 install. If not, say "compile/resolver tests only"; never imply a
live check.

The maintained Windows target is `cstrike_win64.exe`, not WOW64 or the retired
32-bit `hl2.exe`. Live verification must start the game with `-insecure`, arm
all seven feature bits, exercise the changed key/callback path, and end with:

* both prediction sites restored to their exact original branch bytes;
* F6's engine and `d3d9.dll` sites restored when fullscreen code changed;
* no live vtable/code pointer still targeting `bhopfix.dll`;
* `bhopfix.dll` absent from the process after the controller exits.

The full x64 lifecycle was exercised against CS:S build 10897846 on
2026-09-01: exact `-insecure` parsing, both prediction sites and toggles, every
DLL resolver, raw `WM_INPUT` capture, F6/F7 toggles, callback drain, restoration,
and verified DLL unload. CI guards compilation and pure resolver contracts; the
live run remains mandatory after a game update or hook/lifecycle change.

## Cutting a release

Releases are driven entirely by the version in `Cargo.toml`:

1. On `dev`, bump `version` in the root `Cargo.toml` and commit it as
   `chore(release): <version>`.
2. Open a PR `dev` → `main` and merge it.
3. The push to `main` triggers `release.yml`, which:
   - reads the version from `Cargo.toml`;
   - **stops cleanly if the tag `v<version>` already exists**, so a `dev` → `main`
     merge without a version bump is a no-op rather than a duplicate release;
   - builds Linux and Windows x86-64 workspace artifacts;
   - packages `bunnyhopfix` + `libbhopfix.so` and
     `bunnyhopfix.exe` + `bhopfix.dll`;
   - resolves the release notes — a hand-written `## [<version>]` section if
     present, otherwise git-cliff;
   - creates and pushes the tag, commits a generated changelog when needed, and
     publishes both archives plus `SHA256SUMS.txt`.
4. Nothing else is manual. **There is no `git tag` step for a normal release** —
   the tag is an output of the release, not its trigger.

The other two workflows:

- `ci.yml` — pushes to `dev` and `main`, and every PR. Jobs: `commits`,
  `lint`, `test`, native `build-linux`/`build-windows`, Windows
  `cross-windows`, `msrv`, and `changelog-preview`. Windows build artifacts
  always contain both `bunnyhopfix.exe` and `bhopfix.dll`.
- `schedule.yml` — Mondays 05:00 UTC. A `stable`/`beta`/`nightly` rustc canary
  reports toolchain drift, and a rolling prerelease is rebuilt from `dev` only
  when that branch moved. Its Linux tarball and Windows controller/DLL zip are
  CI-clean, not substitutes for the latest human-verified tagged release.

## What a good bug report contains

Use the [bug report template](.github/ISSUE_TEMPLATE/bug_report.md); it asks for
what actually decides these reports:

- **Any tool line containing `FAILED` or `NOT`, verbatim, including the `0x…`
  values.** A game update shows up exactly there: everything is resolved and
  validated before a byte is written, so when a target moves the tool refuses to
  patch and says which one.
- The full output of `BHOPFIX_DEBUG=1 ./bunnyhopfix 2>&1 | tee /tmp/bhopfix.log`,
  from the first line.
- OS/distro, the CS:S build number (the `version` console command — a number,
  not "latest"), the tool version or commit, how it was launched, and whether
  `-insecure` was used.
- `sudo ./verify-live.sh` output if the game was running, and
  `./bunnyhopfix --scan-file <path to client.so>` if the complaint is "the jump
  prediction did nothing".

Nothing is addressed by offset in this codebase, so "it stopped working after an
update" is a signature report, and the lines above are what makes it one.
